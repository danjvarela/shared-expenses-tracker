# AppError messages are user-friendly at the source; diagnostics stay out of the message

Every `AppError.message` is safe to show an end user — no internal ids, config variable names, HTTP status codes, or OAuth jargon — because the presentation layer renders `err.message` verbatim with zero route-level overrides. Internal identifiers are dropped from the message, not preserved elsewhere on the error: a value is only worth keeping for debugging if it is *not already in the request*. A thrown error splits into two kinds:

- **Kind I — value is in the request** (`groupId`, expense `id`, invite `email`, OAuth provider `name`): the constructor takes no argument, the message is hardcoded and friendly, and nothing is logged. The id is recoverable from the route param, form body, or DB row, so dropping it loses nothing for a developer.
- **Kind II — value is infra-internal and not in the request** (missing config var name, upstream OAuth HTTP status): the constructor takes no argument and the message is hardcoded and friendly, *but* the throw site `console.error`s the raw detail before throwing. This is the only place a diagnostic is kept, and it lives in the server log, never the message.

`AppError` itself gains no field — not `cause`, not `detail`. A future `handleError` hook or structured logger would read the same `console.error` output; threading `Error.cause` was rejected as YAGNI until something actually consumes structured error context.

Consequences: the 400-class errors (`GroupHasOutstandingBalanceError`, `InvalidInviteEmailError`, `ExpenseNotFoundError`, `InvalidDefaultSplitError`, `OAuthEmailNotVerifiedError`) and the 500/502 OAuth errors (`UnknownOAuthProviderError`, `OAuthConfigError`, `OAuthTokenExchangeError`, `OAuthUserinfoFetchError`) all carry hardcoded friendly copy and no dynamic arg except `InvalidDefaultSplitError`, which keeps the user's own input `sum` because it is helpful, not internal. A route that needs to surface an error renders `err.message` directly; the settings route's old `instanceof` message overrides are now redundant and get removed in the presentation pass. Status codes are unchanged from before this ADR. If a new error class needs to retain a non-request diagnostic, it must `console.error` it at its throw site — do not put it in `message`.
