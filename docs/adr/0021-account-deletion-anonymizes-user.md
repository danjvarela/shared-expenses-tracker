# Account deletion anonymizes the User

"Delete account" does not hard-delete the `user` row. It anonymizes it: `email` is set to `null`, `displayName` is set to the literal `"Deleted user"`, `deletedAt` is set to the current timestamp, and the avatar columns are nulled (with a best-effort delete of the stored bytes). Every `identity` and `session` row for the user is hard-deleted, so the user is immediately logged out everywhere and the Google link is destroyed — a subsequent login with the same Google identity creates a fresh `User` rather than resurrecting the old one.

The `user` row is kept so that shared history and balance math stay intact. `Expense`, `ExpenseSplit`, `Settlement`, and `PairBalance` rows keep their `userId` references and render as "Deleted user" (the anonymized `displayName`), with no avatar (the serve route returns 404 for the nulled key, so the initials fallback renders "D"). SQLite allows multiple `null` values in a `unique` column, so many anonymized users can coexist without violating the email uniqueness constraint.

`GroupMember` rows are removed only from groups where other members remain. Where the user is the sole member, the membership row is left intact — the group is not deleted. This deliberately bypasses ADR-0011's last-member-leave auto-delete, which only fires through the `kickUser` remove-member path (gated on a nonzero `PairBalance`); anonymize removes membership directly and simply skips removal when the count is one, so a solo-member group's shared history survives the user's departure. The `PairBalance` rows that the sole member had with themselves (or within the group) are kept, since the `User` row still exists.

The avatar delete is best-effort and runs after the transaction: a storage failure does not roll back the anonymize, matching the row-first/best-effort-delete pattern of ADR-0012. The DB writes (identity delete, session delete, group-member removal, user anonymize) run in a single transaction so a failure does not half-anonymize.
