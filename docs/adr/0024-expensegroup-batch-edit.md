# Draft gets add/remove line items; confirmed ExpenseGroups become batch-editable

Two gaps in the scan flow: the draft UI (`scan/+page.svelte`) can only edit the lines a Scanner returned — no way to add a line it missed or remove one it hallucinated — and once confirmed, an `ExpenseGroup`'s child `Expense`s can only be edited one at a time via the existing per-Expense edit page, with no way to add or remove lines from an already-persisted batch. Both gaps get the same fix: extend the batch (draft or persisted) with add/remove, not just per-field edits.

**Draft**: `DraftLine[]` gains push/splice. A new blank line takes empty description, `0.00` amount, no category — same defaults a fresh draft line would get — and inherits the draft's group-level payer/date, same as every other line. Removing is allowed down to zero lines, but Confirm is disabled at zero (nothing to persist). This is purely client-side state; no schema change.

**Confirmed ExpenseGroup**: a new edit page, scoped to any `ExpenseGroup` (not just scan-originated ones — a manually-created one-child group is edited the same way), lets any Group member add, remove, or edit the group's child `Expense`s in one page, mirroring the draft's UX. This needs one new service capability: creating an `Expense` against an *existing* `expenseGroupId` (today `createExpense` always makes a fresh one-child `ExpenseGroup`; only `scan.ts confirmDraft` creates multiple `Expense`s under one shared group, and only at group-creation time). Removing a line reuses `deleteExpense`'s existing pair-balance-reversal logic — but the batch-edit page enforces a floor of 1 `Expense` client-side, so the "delete the parent `ExpenseGroup` when its last `Expense` is removed" behavior in `deleteExpense` (added for the single-expense-delete path) never fires here; emptying a group is a separate, more destructive action than trimming a receipt's line items, not a side effect of it.

`ExpenseGroup` still carries no payer/date fields of its own (ADR-0013) — the draft's single group-level payer/date is a UI convention, not a schema constraint, and each persisted `Expense` already stores its own `paidByUserId`/`date` independently. The batch-edit page keeps the draft's uniform-payer/uniform-date convention (one payer + one date applied to every line) rather than exposing the per-line divergence the schema would technically allow. Real receipts are one purchase from one payer on one day; letting lines drift apart turns "the group this receipt produced" into an arbitrary bag of unrelated expenses, which is a bigger feature than "let me fix what the scanner got wrong."
